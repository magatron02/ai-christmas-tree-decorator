# Product.md — AI Christmas Tree Decorator

## 1. Problem
ร้านขายของตกแต่งต้นคริสต์มาส (เช่นที่จตุจักร) ต้องถ่ายรูป "ต้นที่แต่งเสร็จแล้ว" เพื่อโชว์ลูกค้าว่า element แต่ละชิ้น (ลูกบอล, ริบบิ้น, ไฟ) จะออกมาหน้าตายังไงเวลาใส่บนต้นจริง
- การแต่งต้นจริงแล้วถ่ายทุกคอมโบ (ต้น × element × สี) ใช้เวลาและแรงงานสูง
- ลูกค้าอยากเห็น "ก่อน-หลัง" เพื่อตัดสินใจซื้อ แต่ร้านไม่มีเวลาทำตัวอย่างทุกแบบ

## 2. Solution (แนวคิดหลัก)
เครื่องมือรับ 2 รูป → ส่งออก 1 รูป:
- **Input A**: รูปต้นคริสต์มาสเปล่า (ถ่ายจริงจากร้าน)
- **Input B**: รูป element ตกแต่ง (ลูกบอล/ริบบิ้น/ไฟ — อาจเป็นรูปสินค้าที่มีอยู่แล้ว)
- **Output**: รูปต้นที่ถูกแต่งด้วย element นั้น ให้ดูสมจริง เหมือนแต่งจริง

หลักการ reference คล้าย ChatGPT image-gen ที่รับหลายภาพมา compose เป็นภาพเดียว (multi-image reference → single composited output)

## 3. Target User
- **MVP นี้: ใช้ส่วนตัว** — Altereum ใช้เองที่ร้านจตุจักร ยังไม่ขายให้ร้านอื่น
- (B2B — ขายเป็นเครื่องมือ/บริการให้ร้านค้าอื่นใช้ เลื่อนไปเป็นเป้าหมาย V1.1+ หลัง MVP พิสูจน์ตัวเองก่อน)

## 4. Core Workflow (MVP)
1. อัปโหลดรูปต้นเปล่า
2. อัปโหลดรูป element (1 ชิ้นต่อการรัน 1 ครั้ง — MVP รองรับทีละ element)
3. **Pre-process**: remove background ของรูป element → ได้ PNG โปร่งใส (rembg/Photoshop)
4. เรียก GPT image API (**gpt-image-2**, ผ่าน OpenAI API) ส่งรูปต้นเปล่า + element (โปร่งใส) พร้อม prompt ที่ควบคุมตำแหน่ง/ความหนาแน่นของ element
5. แสดงผลลัพธ์ — เรียงเป็น 3 ภาพ: ต้นเปล่า → element → ผลลัพธ์ (ตามตัวอย่างที่ส่งมา)
6. ดาวน์โหลด/บันทึกภาพ

## 5. Out of Scope (MVP)
- ไม่ทำ 3D rendering หรือ physics simulation ของการแขวนจริง
- ไม่ทำ batch อัตโนมัติทั้งแคตตาล็อกในเวอร์ชันแรก (ทำทีละคู่ก่อน)
- ไม่ทำ e-commerce/payment ในตัว (โฟกัสเครื่องมือสร้างภาพก่อน)
- ~~ไม่ทำ multi-element ในภาพเดียว~~ **→ ย้ายเข้า V1.1 แล้ว (2026-08-05) ดูข้อ 8**

## 6. Decisions Log (ปิดครบทุกข้อ — พร้อมเข้า Architect phase)
- [x] Engine: **GPT image (gpt-image-2)** — ตัวล่าสุด (เม.ย. 2026), OpenAI แนะนำเป็น default production, edit-instruction แม่นขึ้น + คุมความสม่ำเสมอ lighting/composition ข้ามภาพดีขึ้นกว่า gpt-image-1/1.5 — ตรงกับ pain point เรื่อง background/compositing ของโปรเจกต์นี้
- [x] รูปแบบ element input: **ตัด background ก่อน (pre-process)** — remove background ให้เหลือ PNG โปร่งใส (alpha channel) ก่อนส่งเข้า GPT image เพื่อความแม่นยำ/สม่ำเสมอ (ใช้ rembg หรือ Photoshop ที่มีอยู่แล้ว)
- [x] จำนวน element ต่อครั้ง: **ทีละ 1 element ก่อนใน MVP** — เพื่อคุมตัวแปร ทำ prompt ให้นิ่ง วัด success rate ได้ชัด ก่อนขยายเป็น multi-element ใน V1.1
- [x] Output resolution/aspect ratio: **4:5 แนวตั้ง เป็น default → 1536x1920 px** (หารด้วย 16 ลงตัวทั้งสองด้าน, ตรง constraint ของ gpt-image-2, ดูรายละเอียดใน [[Spec.md]] ข้อ 5); เก็บทรงต้นสูงได้ดีกว่า 1:1; MVP ให้ user เลือก ratio อื่นได้เอง ไม่ fix ตายตัว
- [x] ~~โมเดลรายได้: **Pay-per-generation** (คิดต่อภาพ) — ใช้เงินจริงตั้งแต่ MVP แม้เป็นการใช้ส่วนตัว จึงต้องมีระบบ account เก็บ credit balance ตั้งแต่แรก (ดู Spec.md เรื่อง single-account auth) — ยังไม่กำหนดราคา/หน่วย รอ Architect phase คำนวณจากต้นทุน API จริง~~ **← ยกเลิก 2026-08-05 ดูข้อถัดไป**
- [x] **การคิดเงิน: ไม่มี credit balance ในระบบ — ใช้เงินในบัญชี OpenAI ตรง ๆ** (ตัดสินใจ 2026-08-05 แทนที่ข้อบน)
  - **เหตุผลที่เปลี่ยน**: MVP ใช้ส่วนตัวคนเดียว (ข้อ 3) ไม่ได้ขายใคร credit balance จึงเป็นแค่ตัวเลขคู่ขนานที่ต้องคอยกรอกให้ตรงกับเงินจริง ไม่ได้ทำหน้าที่อะไร
  - **ข้อจำกัดทางเทคนิคที่ทำให้ทางเลือกนี้ชัด**: OpenAI **ไม่เปิด endpoint ให้ API key อ่านยอดเงินคงเหลือ** (ตรวจแล้ว: `client.organization` ว่าง, ทั้ง `openai/resources` ไม่มี `billing`/`costs`/`credit_grants`/`balance`) ตัวเลข "เงินเหลือเท่าไร" ในแอปจึงเป็นไปไม่ได้ตั้งแต่แรก
  - **แทนที่ด้วย**: OpenAI เป็นคนบอกเองว่าเงินหมด — ตอบ `billing_hard_limit_reached` แล้วระบบแปลงเป็น error ที่อ่านรู้เรื่อง. ระบบบันทึก `usage` (token) จริงของทุกภาพลง log แทน → รู้ว่า**ใช้ไปเท่าไร** (ไม่ใช่เหลือเท่าไร)
  - **ราคาต่อภาพ**: วัดจริงแล้ว 1536×1920 = input 2674 token (image 2126 + prompt 548) + output 565–1030 token. **`output_tokens` แกว่งทุกรอบ** ทำนายล่วงหน้าไม่ได้ → คิดราคาต่อภาพเป็นสูตรตายตัวไม่ได้ ให้เฉลี่ยจากของที่เกิดจริง (AC-5 จะให้ 30 จุดข้อมูล)

## 7. Success Metric
- ภาพที่ได้ "สมจริงพอขายได้" (ผ่านสายตาคนซื้อของจริง) กี่ % จากการรัน 1 ครั้ง (ไม่ต้อง retry)
  → **วัดรอบแรกแล้ว 2026-08-05: ผ่าน** (30 รูป, ดู AcceptanceCriteria.md AC-5 พร้อมข้อจำกัด)
- เวลาที่ประหยัดได้เทียบกับแต่งจริง+ถ่ายจริง → **ยังไม่ได้วัด**

**สิ่งที่ยังไม่รู้หลังรอบแรก**: การวัดใช้รูป product จากแคตตาล็อก (ต้นบนพื้นขาว แสงสตูดิโอ)
ไม่ใช่รูปถ่ายหน้าร้านจริงตามที่ข้อ 2 กำหนด — ยังไม่มีหลักฐานว่าใช้ได้กับรูปที่มีของรก คนเดินผ่าน
แสงร้านจริง ซึ่งเป็นเคสที่ต้องใช้จริงทุกวัน

## 8. V1.1 — ขยาย scope (ตัดสิน 2026-08-05)

MVP พิสูจน์ตัวเองแล้ว: AC-1 ถึง AC-4 ผ่านครบ, AC-5 รัน 30 รูปจริงแล้วรอกา
เป้าหมายเปลี่ยนจาก **"เครื่องมือแต่งต้นให้ตัวเองดู"** เป็น **"เครื่องมือรับงานลูกค้า"** —
ลูกค้าส่งรูปที่ชอบมา ร้านตอบกลับได้ทั้งภาพตัวอย่างและรายการของที่ต้องใช้

นี่คือการก้าวเข้า B2B ที่ข้อ 3 บอกว่าเป็น V1.1+ ไม่ใช่ scope creep กลางทาง

### 8.1 ข้อมูลสินค้าจาก catalogue
ดึง **รหัสสินค้า + ขนาดจริง** ของทุกชิ้นจาก catalogue 96 หน้า เก็บไว้ในโปรเจกต์

ทำก่อนทุกอย่าง เพราะ unblock ทั้ง 8.2 และ 8.3:
- **8.2 ต้องใช้**: prompt ปัจจุบันบอกได้แค่ *"ให้ได้สัดส่วน"* ลอย ๆ พอมีขนาดจริงจะระบุได้ว่า
  ลูกบอล `017-06` (80 mm) บนต้น `05021-1` (5 Ft = 1524 mm) สูงเป็น **1/19 ของต้น**
- **8.3 ต้องใช้**: จะบอกรหัสสินค้าได้ ต้องมีรหัสอยู่ก่อน

### 8.2 Multi-element (1–5 ชิ้นต่อภาพ)
ผู้ใช้เลือกเองว่าจะใส่กี่ชิ้น ตั้งแต่ 1 ถึง 5

**ข้อกำหนดคุณภาพเข้มขึ้นจาก MVP**: แสงเงาและขนาดของทั้ง element และต้น **ต้องเป๊ะ**
ไม่ใช่แค่ "ดูโอเค" — ยังไม่ทำ 3D rendering / physics simulation (ยังอยู่ Out of Scope)
ความเป๊ะมาจากตัวเลขขนาดจริงใน 8.1 ที่ป้อนเข้า prompt ไม่ใช่จากการจำลองฟิสิกส์

**ผลข้างเคียงที่ต้องยอมรับ**: baseline ของ single-element ที่ AC-5 กำลังวัดจะใช้เทียบกับ
multi-element ไม่ได้ ต้องมี AC ใหม่แยกสำหรับ multi

### 8.3 Reference image
ผู้ใช้แนบรูป ref จากลูกค้าเข้าไปในการ gen ใช้ทำ 2 อย่าง:

1. **จำลองสถานที่** — สร้าง BG ตามโทน/สไตล์ของรูป ref แล้ววางต้นที่แต่งแล้วลงไป
2. **แกะของตกแต่งจากรูป** — บอกว่าในรูป ref มีของแบบไหน หาของใกล้เคียงที่สุดในแคตตาล็อก
   ตอบกลับเป็น **รหัสสินค้า + ปริมาณที่ควรใช้**

**กฎความมั่นใจ (ตัดสิน 2026-08-05)**: เสนอ **top-3 พร้อมคะแนน** เสมอ ห้ามตอบตัวเดียวแบบมั่นใจ
ถ้าคะแนนต่ำกว่า threshold ต้องบอกตรง ๆ ว่าไม่เจอของใกล้เคียง
— **รหัสผิดคือลูกค้าสั่งของผิด** ความเสียหายตกที่ร้าน ไม่ใช่ที่ระบบ

**หมายเหตุ**: ข้อ 8.3.2 เป็นคนละเทคโนโลยีกับที่มีอยู่ ไม่ใช่การต่อยอด prompt แต่เป็น
image similarity search ต้องมี embedding index ทับสินค้าทั้งแคตตาล็อก

### สิ่งที่ได้
1. ลูกค้าส่งรูป ref → ได้ภาพตัวอย่างการแต่งประกอบการตัดสินใจ
2. ร้านรู้รหัสสินค้าและจำนวนที่ต้องใช้ตามรูปที่ลูกค้าให้มา
3. ได้ภาพต้นที่แต่งเสร็จวางในสถานที่ตามรูปตัวอย่าง
